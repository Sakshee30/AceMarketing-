1. Objective and honest completion standard
Qualify AceMarketing on isolated, production-like infrastructure with synthetic data before exposing real customers, advertising accounts, payment activity or messaging recipients. The objective is to uncover and resolve structural, business-logic, integration, security, data-quality and operational defects early, leaving only explicitly identified account/environment checks and accepted minor issues for a controlled-live phase.
This package is a test strategy and starting execution catalogue, not a claim that the application is tested or production-ready. It contains 356 planned scenarios, 28 coverage obligations, 13 declared provider connector test sets, 13 phases and 12 release gates. The counts describe this planning catalogue, not every possible input combination or a completed inventory of every route. Phase P0 must reconcile all actual routes, UI actions, operations, jobs, schemas, migrations and advertised capabilities against it. Newly discovered scope adds tests; it does not disappear to preserve a percentage.
No application feature test, provider sandbox test, load test, scan, restore or deployment was performed for this plan. Selected repository files and existing CI results were inspected. One limited static check was performed: a decoded source excerpt of the connector-ingestion imports failed Node syntax checking. No repository files were modified, no CI job was triggered, and no external business action was taken. [S01–S15]
A reliable end state is evidence-based: each release-scope requirement has an owner, acceptance criteria, selected tests, reproducible data, actual execution status, defects and final candidate evidence. No finite test programme proves that only minor live changes will remain. Any major issue uncovered in later sandbox/account validation reopens the relevant pre-live phase and blocks that capability.

3. Scope model: how “everything” becomes measurable
Create a machine-readable scope ledger from six inputs: public and private routes; visible controls and form states; backend operation/router registrations; database tables/migrations; workers/schedulers/realtime events; and module/connector/capability manifests. Compare this implementation inventory with marketing claims, README descriptions and intended user journeys. A declared feature without reachable implementation is either fixed for the release or explicitly removed/disabled with product approval.
For every operation, record the request method/path or event name, owner, input schema, auth requirements, tenant and field boundary, business preconditions, persistence, downstream effects, failure states, rate/quota policy and applicable deployment modes. Map it to requirements and automated/manual tests. Avoid relying only on button counts or code coverage.
Classify each item as implemented-unverified, passing on the candidate, failing, blocked by a dependency, intentionally unsupported, or excluded with documented approval. Keep declared capability, implementation state and qualification state in separate fields. A test that is not run is not passed. A module disabled by the current mode is not “tested successfully”; its disabled behavior is a separate test.
Use exhaustive boundary and state-transition tests for critical deterministic logic. Use risk-based pairwise combinations for lower-risk browser/configuration combinations, but explicitly enumerate critical tenant × role × write/read/export × capability combinations. Test data covers empty, normal, limit, over-limit, malformed, duplicate, reordered, stale, unauthorized and interrupted cases.
The companion workbook contains the initial coverage ledger and executable scenario descriptions. Its dashboard reports catalogue execution progress, not an independently established percentage of the entire application.

5. Qualification tiers and safe environments
Tier A — Offline application qualification.
 Run real frontend artifacts, real APIs, real PostgreSQL, real workers, scheduler and applicable object/AI services. Substitute only external providers with deterministic local simulators. Do not intercept the application's own API responses in acceptance E2E tests. Browser API mocking remains useful for isolated UI/component tests, but those results must be labeled separately. Playwright recommends controlling third-party dependencies for repeatable testing. [S17]
Tier B — Authorized provider sandbox qualification.
 After Tier A, run separately authorized developer/test-account checks where the provider offers a suitable safe environment. This tier is not part of the work performed for this plan. Do not assume every provider has a sandbox or that it supports every operation. Record the exact account, API version, scopes, callback configuration, operation and limitations. A provider without adequate safe qualification remains blocked/disabled rather than falsely green.
Tier C — Controlled-live acceptance.
 A later, independently approved activity for actual infrastructure/account permissions and narrowly bounded real outcomes. It is not run by this pre-live pipeline. No automatic advertising spend, live conversion uploads, paid messaging, production charges or customer-data use is authorized by this plan.
Provision ephemeral run-owned functional environments and longer-lived disposable performance/recovery environments. Use separate test databases, object buckets/prefixes, encryption keys, secrets, DNS names, mail capture and provider accounts. A job must verify both a configured allowlist and an environment identity marker before seeding, destructive tests, scanning, load or restoring. Hard-deny production credentials/accounts/destinations. Enforce egress at the network layer as well as in code; a single environment flag is not enough.
Use valid test TLS and a test-only trust configuration for HTTPS-only connector simulators. Do not weaken production SSRF/HTTPS validation just to make tests pass. Record allowed simulator endpoints and reject redirection outside them. Unknown endpoint overrides fail closed. Secrets are injected through scoped Jenkins credentials, never committed or printed. Untrusted pull-request jobs receive no provider/release secrets and no privileged deployment agent. [S16, S24]
The embedded PostgreSQL-compatible local store described in the README is useful for developer smoke tests. It does not substitute for real PostgreSQL qualification with a production-like application role, locking, pooling, transactions and RLS. PostgreSQL superusers and BYPASSRLS roles bypass RLS, as do table owners normally; test the actual restricted runtime role and record its attributes. [S05, S19]

8. Functional/API test pattern for every feature
Each discovered feature gets positive, negative and lifecycle coverage. Verify create/read/update/delete or the feature's actual equivalent, field validation, required/optional/default values, boundary lengths, Unicode, time/currency handling, pagination/filtering/sorting, empty/loading/error states, duplicate submission, stale version and concurrent mutation. Do not mechanically impose CRUD where an append-only audit/event object has different intended semantics.
API tests validate schema, status, content type, meaningful error shape, authorization, idempotency and side effects. Include unknown fields/mass assignment, wrong tenant, wrong role, expired credentials, invalid resource parent, optimistic-lock conflicts, payload limits, rate limits and partial failure. A 200/202 response alone is never sufficient: inspect actual persistence, asynchronous completion and visible business output.
Use the existing Node test runner and Python pytest stack. Add frontend component tests where needed, keeping component-level mocks separate from true E2E. Playwright can cover browser flows and API request-based assertions; a duplicate Postman/Newman suite is optional for teams that need shareable API collections, not an automatic second source of truth. Reuse existing contract/architecture/AI scripts after reviewing their actual assertions and discovery coverage. [S04, S12]
Discover all test files and compare to explicit script selections. The pipeline must fail on accidental 
.only
, unapproved skips and missing required suites. Tests with unmet prerequisites report BLOCKED, not PASS. Retry results remain visible; a pass only after retry is FLAKY pending triage. Critical flaky tests cannot be quietly quarantined out of a release gate.
9. Mandatory end-to-end business journeys
J01 — First-time organization to trusted report.
 Create a synthetic organization/workspace; onboard actual-role users; connect a provider simulator; backfill known campaign/CRM data; ingest a tracked visit and lead; qualify/convert; reconcile the dashboard and export. Verify UI → API → raw/canonical database → worker/scheduler → report. No application API mock may supply the success result.
J02 — Paid click to conversion signal return.
 Capture synthetic click identifier; stitch the authorized identity; create lead and qualified outcome; compute attribution; prepare approved conversion; dispatch only to simulator; inspect acceptance/rejection/unknown-outcome ledger. Repeat with response loss and duplicate retry. Assert one logical effect, correct value/currency/time and accurate visible receipt.
J03 — Consent withdrawal during queued work.
 Queue audience/message/AI activation; revoke consent and remove user authorization before dispatch; resume worker. Assert that dispatch-time safety and suppression rules prevent prohibited effects, with clear status and audit history.
J04 — Historical sync to incremental recovery.
 Backfill multiple pages, fail a middle page, restart worker, resume from safe checkpoint, receive late updates/deletes and replay a duplicate page. Reconcile source totals and canonical records; no skipped or double-counted history. Freshness and partial-state labels must be correct.
J05 — Form/rule/workflow/approval.
 Publish versioned form, submit, evaluate rules, obtain permitted approval, crash after one committed step, resume and perform one simulated action. Change workflow version while approval is pending and verify the frozen-run policy. Self-approval and wrong-tenant decisions must fail.
J06 — Safe AI analysis and activation.
 Ingest known source data and approved documents, ask a grounded question, inspect query/source lineage and model/prompt versions, generate a recommendation, reject unauthorized execution, approve valid proposal and dispatch to simulator. Repeat with injected instructions, unavailable data, timeout and disabled kill switch.
J07 — Subscription and quota correctness.
 Create test subscription, replay verified billing events, consume quota concurrently, fail/cancel operations, reconcile usage and downgrade plan. No real charge is made; double billing and unauthorized entitlement changes are blockers.
J08 — Collaboration under conflict.
 Two users move the same board item and modify shared state while a third reconnects after losing events. Verify conflicts, idempotency, replay/snapshot recovery and cross-tenant realtime denial. Repeat after membership revocation.
J09 — Document to authorized search and deletion.
 Upload, quarantine, approve/process/index, retrieve through authorized search/AI, then revoke access and delete. Verify metadata, object storage, search projection, caches and retrieval honor the lifecycle and cannot reveal foreign documents.
J10 — Multi-channel lead journey.
 Simulate WhatsApp messages, call callbacks, meeting booking and CRM updates for the same approved fixture identity. Check status ordering, timezone, consent, source lineage and attribution without contacting actual recipients.
J11 — Security boundary journey.
 Tenant A attempts all critical read/write/export/search/realtime/AI/admin operations using tenant B identifiers. Exercise real HTTP requests and the restricted database role. Zero cross-tenant disclosure or mutation is tolerated.
J12 — Operational recovery journey.
 Run representative workload; record acknowledged IDs; stop worker/API/database; restore service or recover to a clean host; replay eligible work; reconcile data, usage and provider receipts. Then prove a compatible app rollback and non-destructive mode downgrade.
Every journey attaches a correlation ID, exact seed/version, identity/role, request traces, durable state comparison, worker or provider ledger, UI evidence and audit entries. A screenshot and a green toast without backend proof are insufficient.
10. Provider-specific contract and integration qualification
The inspected connector registry lists Meta Ads, Google Ads, X Ads, TikTok Ads, LinkedIn Ads, GA4, HubSpot, Salesforce, Zoho CRM, Pinterest Ads, Microsoft Ads, WhatsApp Cloud and Custom HTTPS. These are declarations to reconcile, not provider-verified capabilities. The workbook has eight planned scenario families for each. Billing, email, call and calendar transports have separate business-flow tests anchored in project scripts/module references. [S04–S07]
For each connector, separately record authentication, account binding, read, write, history/backfill, incremental synchronization, webhook, deletion/correction, rate limits, version and native/bridge implementation. An unsupported operation is explicitly N/A with rationale. For example, do not require a read-only analytics connector to support campaign writes, or invent webhook support where none is declared.
The core simulator matrix includes valid response, empty response, invalid schema, missing fields, unknown fields, malformed body, invalid token, expired token, revoked permission, wrong account, 429/Retry-After, 5xx, timeout, connection reset, duplicate page/event, repeated cursor, partial batch failure, delayed/out-of-order callback and response loss after acceptance. Test custom report downloads for redirect/DNS restrictions, content/expansion limits and safe failure.
Prove that cursor advancement and normalized state commit safely; replay must not skip records or duplicate money/conversion effects. Separate provider acceptance from final delivery, and treat unknown external outcomes as reconciliation work before retrying a potentially irreversible action. Maintain a provider simulator request/receipt ledger independent of the application database.
Validate the registry, customer UI, account verifier, runtime handler, worker dispatch and source-normalization behavior against the same capability matrix. A connected OAuth credential is not evidence that data is actually being ingested. A native/bridge reporting claim needs handler and execution evidence. Do not inherit older assumptions about Microsoft/X or any other connector from documentation without inspecting the current implementation.
Tier B later validates real test-account limitations and API version contracts against official provider documentation. Record all live-only residual checks; no expectation of a safe sandbox is assumed. Live credentials and production accounts are never inserted into ordinary pull-request, nightly or offline-release jobs.
11. Data correctness, identity and analytics
Test first-party identity capture, anonymous-to-known linking, false-merge resistance, shared devices, cross-device authorized joins, late/out-of-order events, duplicate events and missing identifiers. Tenant context is part of every join and derived record. A plausible-looking journey must not hide incorrect identity merges.
For each supported attribution model, build a hand-calculated expected journey, including eligible/ineligible lookback touches, direct/unknown traffic, repeated touches, multiple conversions, refunds/corrections, and missing channel information. Assert conservation of eligible credit and approved rounding. Define what changes when late data arrives and whether reports are versioned/recomputed.
Compare raw provider payloads, canonical records, CRM outcomes, attribution results, dashboard figures, exports and AI-referenced metrics. The metric catalogue's zero-denominator, currency and time-window rules are explicit acceptance inputs. Investigate differences between net and gross definitions, not just numerical equality on refund-free fixtures. [S15]
Test timezone offsets, daylight-saving boundaries where supported, start-inclusive/end-exclusive windows, future timestamps, clock skew, numeric precision, negative corrections and null fields. Invalid data must be rejected/quarantined or labeled according to a reviewed rule; silently converting malformed values to zero can conceal broken ingestion and must be reviewed.
No predictive/model-generated conversion or revenue estimate is allowed to masquerade as a recorded payment. Reports must expose source freshness, partial synchronization and insufficient-data states. No local demo fallback should appear as live customer analytics in production-mode qualification.
12. AI and ML qualification
Keep three independent evidence types: deterministic orchestration/contract tests with simulated model responses; real model runtime and safety tests in an approved isolated environment; and statistical business-quality evaluation on representative labeled/held-out data. Success in the first category is not model-quality evidence, and synthetic data alone cannot demonstrate forecasting, causal or marketing effectiveness.
For analyst/knowledge features, test tenant-scoped retrieval, field authorization, grounded numeric answers, source/query lineage, data freshness, absent information, malicious document/provider instructions, tool permission enforcement, allowed destinations, output schema, streaming disconnect, cancellation, token/cost budgets and secrets in logs. Approval, consent, quotas and kill switches are enforced at dispatch, not only when generating an AI proposal.
For each enabled scoring, forecasting, causal or MMM feature, define task-specific metrics and a simple baseline before evaluation. Record dataset provenance, label quality, minimum sample conditions, training/validation/test partitions, temporal/tenant separation, leakage checks, model/prompt/checkpoint versions, random seeds and applicable uncertainty. Review weak segments and calibration; avoid a universal “AI accuracy” percentage across unrelated tasks.
Test model loading, incompatible/corrupt/missing checkpoints, unavailable specialist dependencies, resource admission, retry limits, version routing, promotion approval, rollback and deletion. Frozen jobs must retain their intended model/config lineage. Live-model output may need repeated statistical evaluation rather than exact text equality. Unsupported/disabled specialist functions must return an honest unavailable state.
The existing Python workflow and Node AI scripts supply useful starting checks. Audit path-filtered triggers so backend/client changes that alter ML contracts still select the relevant cross-service tests. Never use a stale trained-model report to qualify a different candidate or checkpoint. [S04, S06, S12]
13. Security, privacy and abuse-resistance programme
Use a proposed OWASP ASVS 5.0.0 Level 2 requirements map, adjusted by the threat model and actual release scope; it is a testing baseline, not a certification claim. Combine code/dependency/image/secret scanning with authenticated dynamic scans and manual business-logic abuse tests. Automated scanners alone will not establish tenant isolation, correct approvals or billing safety. [S18, S24]
Critical boundaries include authentication/recovery, role/resource/field authorization, organization/workspace context, object downloads, search/AI retrieval, realtime subscriptions, connector credentials, custom outbound destinations, inbound signatures, usage reservations and privileged control APIs. Exercise absent/wrong tenant context through real restricted database roles and shared pools/workers. [S19]
Test safe injection fixtures, stored/reflected XSS, mass assignment, path traversal, unsafe archive expansion, SSRF/private-IP/metadata/DNS rebinding, cross-origin/CSRF behavior where applicable, callback replay, session revocation, exposed secrets and denial-of-service limits. Active scanning and adversarial workloads run only against allowlisted disposable systems under agreed limits.
Privacy coverage includes consent version and purpose, withdrawal before dispatch, subject export, erasure across derived data/search/AI/queues, retention schedules, authorized holds, log/report redaction, evidence access and deletion after backup restore. Establish the applicable privacy requirements with the responsible owner; this plan does not assert compliance with a jurisdiction or legal regime merely because technical tests pass.
Scan runtime and build/dev dependencies, generated browser assets and OS/container packages; a production-only npm audit is not the entire supply-chain review. Tie SBOM and scan evidence to the exact artifact. Findings require severity, exploitability/reachability, owner and disposition; scan failure or stale database must not be interpreted as “no vulnerabilities.”
14. Browser, accessibility and human testing
Run critical user journeys across Chromium, Firefox and WebKit against production-built artifacts. Add actual supported Edge/Chrome channels and real Android/iOS browser checks according to the support policy. Playwright browser/device emulation is useful but must not be labeled testing of physical phones or native mobile apps. The existing single-file browser matrix is a start, not complete cross-browser regression. [S10, S11]
Automate axe checks on relevant UI states and perform manual keyboard-only, screen-reader, focus-order, dialog, error-message, zoom/reflow and non-drag board movement checks. Automated accessibility tools do not detect every accessibility problem; manual and inclusive user evaluation remain necessary. Proposed acceptance target is the applicable WCAG 2.2 AA criteria, with exact requirement mapping and exceptions reviewed rather than assumed from an axe score. [S21]
Visual regression uses approved baselines with deterministic data, time, font and viewport settings. Dynamic content is controlled without masking the element being tested. Snapshot approval requires review; it cannot waive a functional or accessibility defect.
Exploratory sessions exercise interruption, slow network, refresh/back navigation, long sessions, multiple tabs, workspace switching during requests, inconsistent input and recovery from errors. Human UAT is performed by business personas on realistic synthetic data. A new operator also validates installation/restore/runbooks without relying on the original developer's memory.
15. Performance, scale and resilience
Approve workload, hardware, data volume and per-operation objectives before calling a run passing. The repository's 4,000-RPS default and capacity-budget calculations are configuration targets, not demonstrated throughput. Distinguish concurrent users, offered arrival rate, completed requests and completed business operations. A test of forms/read endpoints is not equivalent to validating the whole marketing pipeline. [S13, S14]
Proposed initial exploration includes 1/10/50/100 concurrent-user steps, steady authenticated mixed traffic, ingestion bursts, queue/backfill workloads, search/export/document/AI resource contention and a noisy-neighbor tenant. Choose eventual arrival-rate targets from business needs and measured hardware. Do not force a default 4,000-RPS claim onto an unqualified environment.
Suggested starting acceptance budgets, subject to approval, are ordinary authenticated interactive API p95 ≤ 500 ms and p99 ≤ 1,000 ms, unexpected business failure < 0.1%, and critical non-AI async completion p95 ≤ 60 seconds under the agreed workload. Long exports, document processing, AI inference and cold starts require separate budgets. These are proposed targets, not measured performance or universal requirements.
Require no dropped load-generator iterations at the qualification target; record generator CPU/network utilization and achieved request rate. Use threshold-gated checks for business correctness and distinguish expected rate limiting during overload from unexpected failure at the agreed load. k6 thresholds provide pass/fail decisions; plain response checks alone are inadequate. [S20]
Run stress-to-break, spike-and-recover, approved multi-hour soak, worker crashes, lease contention, database interruptions, object-store outages, disk pressure and retry storms. Measure connection pools, queue age, memory, CPU, event-loop lag, DB locks/slow queries and final record counts. Verify every acknowledged durable event is recoverable and logical irreversible effects are deduplicated.
A 2xx/202 acknowledgment is only the first timestamp. Record source received → persisted → queued → processing → completed → visible-on-dashboard durations. After every load/chaos run, reconcile money, quotas, conversion receipts, tenant ownership, dedupe keys and counts independently. No corruption, cross-tenant leakage, duplicate charging or unexplained acknowledged-event loss is acceptable.

18. Test-case record and evidence contract
Every execution record includes test ID, requirement ID, feature/operation, risk priority, phase/layer, exact SHA, environment/mode/capability fingerprint, fixture version/seed, actual role/account, prerequisites, actions, expected/actual result, start/end timestamps, attempt/retry history, status, defect IDs, evidence hashes and reviewer. Capture method/path/event/version as P0 discovers them; do not invent routes merely to fill a spreadsheet.
Allowed statuses are NOT RUN, PASS, FAIL, BLOCKED, FLAKY and NOT APPLICABLE. Non-applicability requires a reason and approval; disabled-feature behavior is still tested. An unmet environment or provider prerequisite is BLOCKED, not PASS. Mock-only, sandbox and live evidence are separate qualification fields rather than interchangeable results.
Evidence for a business test includes sanitized API trace, UI trace/screenshot where useful, database or authorized read-model result, worker completion and provider simulation receipt, plus audit/correlation IDs. Security/load/recovery tests add the exact scan configuration, hardware, offered/achieved rate, measurements, restore manifests and checksums. Retain enough context to reproduce a failure while protecting secrets and synthetic sensitive canaries in shared reports.
Use per-run paths such as 
artifacts/qualification/<sha>/<run-id>/
 with a manifest linking all files. Sign or otherwise protect the final evidence packet against accidental mutation. Expire routine detailed traces according to a reviewed retention policy while retaining final release decisions and necessary audit evidence. No numerical coverage claim may exclude blocked/skipped requirements without disclosing the denominator.
19. Defect remediation and change control
The initial findings register distinguishes observed defects, CI/environment blockers and qualification gaps. All are Open, not silently resolved. Prioritize P0 boot/auth/tenant/data-loss/unsafe activation issues, then high-impact functional and operational issues. Do not spend extensive effort executing downstream E2E while the application cannot parse/start.
For each defect capture reproducible steps, actual versus expected behavior, affected version/mode/roles, source evidence, business impact, root cause, fix owner and required regression. Fix one root cause rather than weakening assertions or painting the UI green. A backend/API contract or schema change triggers relevant clients, workers, model contracts, migrations and backward-compatibility tests.
A defect closes only after a verified fix on the candidate, reproduction no longer fails, affected regression passes and a reviewer confirms the intended behavior. Later changes invalidate earlier evidence for affected scope. The final release candidate is rebuilt once into immutable artifacts and retested; it is not assembled from successful tests across unrelated commits.
Critical/high-impact unresolved defects block release. Minor accepted issues need a documented workaround, owner, rationale, affected scope and resolution review date; “minor” does not include tenant leakage, wrong money/metrics, unsafe sending, broken recovery or untested mandatory functionality. Flaky test quarantine requires owner and alternate evidence; it cannot bypass a mandatory critical gate.

Code coverage can be a supporting regression indicator; define thresholds after measuring honest baseline and exclude generated code transparently. It does not prove requirements coverage. If adopting an initial target, consider ≥80% line and ≥75% branch coverage in testable business modules and ≥90% branch coverage for critical deterministic validation/auth/metric logic, with reviewed exceptions. These are proposed targets, not observed values or universal quality rules. Mutation/property tests should challenge important calculations, policies and state transitions.
For Tier A acceptance, all mandatory offline tests and evidence must pass, and external providers remain visibly simulated/unqualified with live operation disabled. For Tier B acceptance, each enabled connector additionally needs relevant authorized test-account evidence. Production enablement is a different decision requiring environment/account-specific checks and approvals. No provider earns “production verified” from mock responses.
Final signatories are QA, product, engineering, security for applicable risk, and operations for deployment/recovery. The report states exactly what was tested, not run, blocked, excluded, flaky and accepted. It names any remaining changes and their impact; there is no blanket guarantee of zero future defects.
22. Immediate implementation order
First correct F01 and F02 and rerun complete syntax/import/startup validation on the frozen or new reviewed revision. Then establish the supported runtime and production-like authenticated PostgreSQL lane. Next build the target-safety, seed/reset, simulator and evidence harness; map the existing scripts into Jenkins without duplicating GitHub Actions logic.
After that, reconcile scope and start with tenant/auth/data correctness, provider ingestion and metric oracles before broad UI automation. Add complete business E2E, then workflows/AI/files/control safety, followed by browser/accessibility, security, load/resilience and the Docker/native install and recovery matrix. Resolve root causes and rerun affected plus full critical regression after each candidate change.
Conclude with human synthetic-data UAT and a reproducible pre-live evidence packet. Only then separately authorize provider test-account qualification. Anything discovered there that changes core logic returns to the relevant pre-live phase; it is not dismissed as a minor live tweak.
