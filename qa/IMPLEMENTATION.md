# Pre-live test implementation and qualification boundaries

This branch implements an executable pre-live test foundation, not an assertion that all 356 supplied acceptance scenarios are complete. Do not merge or enable production because a test job is green. See the candidate-specific artifacts and `release-evidence-gate.json`.

## Repeatable execution

On a dedicated disposable Linux runner, install the locked Node dependencies, the approved Node 24.21.0 runtime, PostgreSQL 16 server tools, and the three Playwright browser engines with their operating-system dependencies. Run as a non-root user with permission to create a network namespace:

```sh
npm ci
npx playwright install --with-deps chromium firefox webkit
bash qa/run-isolated.sh
```

Dependency installation occurs before isolation. The application test process runs inside a fresh loopback-only network namespace with an explicitly cleared environment. It creates its own temporary PostgreSQL cluster and database names, never accepts a caller database target, and does not receive production provider credentials. The runtime API uses a separate non-superuser, NOBYPASSRLS role with authentication enabled. Native repository tests use separate per-file bootstrap-role databases; these are not substitutes for the restricted-role API security checks.

The checked-in `qa/Jenkinsfile` orchestrates the same runner. It must be connected to an actual Jenkins job/agent before Jenkins execution can be claimed. The GitHub workflow `.github/workflows/prelive-qualification.yml` provides another execution route. Neither route deploys production. Repository workflow preparation is read-only; the one-time reviewed source-patch bootstrap has been removed.

## Implemented layers

- Recursive JavaScript syntax discovery; all discovered native Node test files, not just the package script's handpicked subset.
- Independent golden metric, token-integrity, event validation, streaming-client and workspace-visibility tests.
- Real PostgreSQL migrations and repeat migration, per-file native test databases, independent frontend type/build checks and architecture checks.
- Supplied core-fixture seeding with exact role mappings. Unmapped viewer/approver/support/billing personas remain explicitly unresolved; no artificial privilege expansion.
- Real authenticated HTTP acceptance tests for selected APIs and business paths, including a 100-row supplied-lead API subset, authorization denial, actual worker completion and persisted readbacks.
- Production-built browser tests in Chromium, Firefox and WebKit. Browser counts include separate route checks and project repetitions, not that many unique end-to-end business journeys. No mocked successful application API responses are used in this lane.
- A real in-cluster PostgreSQL dump/restore, table-content reconciliation and authenticated restored API smoke. This is not a fresh-host disaster-recovery, object/key backup or installation matrix qualification.
- Separate dependency-audit and Python ML checks, with actual reports. ML synthetic mechanics are not real-world efficacy evidence.

## Added full functional data-layer integration

`backend/tests/functional-volume.test.mjs` is automatically discovered by the isolated native runner. It regenerates the original D2 files using the supplied generator and verifies five original SHA-256 hashes before any data loading. The fixed fixture history and minor-to-major INR conversion are explicit.

It then exercises the real lead and tracking-event repositories against a fresh PostgreSQL database: 10,000 leads, 100,000 events, replay of 1,000 leads and 1,000 events, exact ID/scope/field/hash checks, per-workspace counts, event-type totals, payment/refund/net-revenue reconciliation, read caps and empty-workspace behavior. The expected reconciliation file is locked to the supplied package rather than generated by the application's metric calculator.

This is data-layer integration. It does not prove every lead/event travelled through the browser or HTTP importer. It does not qualify performance SLOs, production capacity or RLS by itself. The 100 campaign and 9,000 provider-daily records are reproduced for provenance but are not yet imported by this data-layer test. The one-million-event D7 profile is available in the generator but is not part of this lane. Source fixtures are created under the temporary run directory and removed with that directory.

## Connector regressions and repairs

`backend/src/connector-http.mjs` enforces an explicit HTTPS-origin allowlist, blocks embedded URL credentials and cross-origin redirects, bounds same-origin redirects and response bytes, includes body streaming in the overall deadline, and rejects malformed/non-object/non-JSON successful responses. HTTP errors preserve status and Retry-After without including raw provider bodies.

`backend/tests/connector-http.test.mjs` covers 24 deterministic external-transport cases. `backend/tests/connector-pagination.test.mjs` exercises actual sync orchestration and real PostgreSQL with only the external provider fetch simulated. It covers Meta pagination/deduplication, repeated cursors, configured page truncation, second-page failure and recovery, malformed and invalid schema responses, explicit valid empty results, and invalid Google Ads/GA4 response structures. Failed/incomplete histories must not advance their checkpoint or be labelled synchronized.

These tests are not a verified native wire-contract suite for every one of the 13 providers, and are not sandbox or live account qualification. Further provider field-level, callback, signature, backfill/deletion and version cases remain in the source acceptance catalogue.

## Evidence and status

`artifacts/prelive` contains the candidate SHA, immutable source archive, source discovery, sanitized logs, JUnit, business readbacks, browser report, restore reconciliation, functional-volume results when available, and checksums. Raw ephemeral credentials and database dumps stay outside published reports. Failed stages retain evidence; later independent checks can still run.

`source-case-status.json` retains all 356 supplied test IDs. Supporting implementation evidence is linked without automatically converting a broad acceptance scenario to PASS. `scope_complete` remains false unless its entire defined requirement has been executed and reviewed. `release-evidence-gate.json` fails closed for missing, incomplete, failed, skipped or unapproved scope. Run-level test success and release approval are different results.

Still required before full offline qualification: completed route/operation-to-scenario inventory; remaining persona and provider adapters; full business/UAT journeys and file corpus; all declared provider failure contracts; security/privacy review and scoped dynamic scans; manual accessibility/real-device checks; approved load/stress/soak/chaos scenarios; all supported deployment modes and fresh-host recovery; actual model safety/quality evaluation and human sign-off. Live-provider qualification requires separate authorization and safe accounts.
